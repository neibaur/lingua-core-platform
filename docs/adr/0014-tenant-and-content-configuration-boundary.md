ADR-0014 — Tenant and Content Configuration Boundary
Status: Accepted
Phase: Phase 15
Supersedes: —
Related: ADR-0013 (UI/API Delivery Boundary); ADR-0012 (Search-to-Learning Integration Boundary); ADR-0011 (Learning Surface Layer Structure)

Context
The deterministic pipeline currently terminates at the Phase 14 route delivery contracts — ReadingPrimitiveSearchProjectionRouteDeliveryContract, WritingPrimitiveSearchProjectionRouteDeliveryContract, and SpellingEntrySearchProjectionRouteDeliveryContract (confirmed from source: the three *-route-delivery-contract.ts files in src/core/tokenizers/search/query-learning-interop/, each a structural artifact carrying {schemaVersion, deliveryId, searchProjection, staticContentAddress} and built by a compose*RouteDeliveryContract builder). Phase 14 is COMPLETE; the remaining chartered delivery categories are deferred (SESSION_STATE.md — Current Phase and Status; Deferred Scope).

ARCHITECTURE.md anticipates a layer beyond delivery: "Tenant and content configuration (Phase 15 — deferred) consumes delivery contracts without reaching through Phase 13 internals" (ARCHITECTURE.md — Delivery Boundary Layer / Layer Position). The platform's tenant model is sketched conceptually in ARCHITECTURE.md — Multi-Tenant Routing Concept and ARCHITECTURE.md — Database Blueprint, and the learning-surface ADRs explicitly assign "lesson grouping, sequencing, tenant-specific weighting, and curriculum organization" to Phase 15 (ARCHITECTURE.md — Learning Surface Layer / Scope Boundaries; ADR-0011 Decision §3). No structural seam, type, or contract for tenant or content configuration exists in the repository today (confirmed by source scan: the string "tenant" does not appear anywhere under src/core). That structural gap is the subject of Phase 15.

Phase 15 is authorized for ADR-0014 boundary drafting only (SESSION_STATE.md — Current Phase and Status; ROADMAP.md — Phase Status). This ADR establishes the architectural boundary and grounding vocabulary for Phase 15. It does not authorize implementation of any Phase 15 slice: as with ADR-0011, ADR-0012, and ADR-0013, acceptance of a boundary ADR does not by itself authorize code; every slice remains governed by a repository-first pre-implementation assessment per HANDOFF_TEMPLATE.md §9 and explicit operator authorization before any code is written (cf. ADR-0013 Context — "Acceptance of this ADR does not by itself authorize implementation of any Phase 14 slice"). This ADR proposes no type names, field names, interface members, builder signatures, or structural payload shapes; all such shapes are deferred to per-slice pre-implementation assessment under the DOCUMENTARY DERIVATION LAW and TYPED REFERENCE LAW (HANDOFF_TEMPLATE.md §3).

Decision
Phase 15 introduces deterministic structural configuration contracts representing tenant and content configuration. These contracts form a structural seam only. They are not a tenant-resolution engine, a routing layer, a middleware stack, or a runtime configuration evaluator. The boundary is constrained as follows, each constraint grounded by citation or named law.

1. Structural configuration contracts only; no runtime resolution.
   Phase 15 delivers structural types and deterministic builders that represent tenant and content configuration as data. It does not perform tenant routing, hostname/domain resolution, middleware request handling, request-context application, feature-flag runtime evaluation, content-visibility runtime resolution, or any runtime selection of configuration. Any field, function, or contract shape that would require runtime resolution to produce a meaningful result is out of scope.
   Grounding: STATIC RESOLUTION LAW — prohibits "plugin systems, runtime registries, ambient runtime discovery, dependency injection containers, mutable singleton state, or async orchestration," and mandates "explicit orchestration, static composition, deterministic layering, discriminated unions, and readonly contracts" (HANDOFF_TEMPLATE.md §3). The ARCHITECTURE.md — Multi-Tenant Routing Concept describes a runtime flow ("Browser request → Hostname or domain → Middleware → Resolve tenant configuration → Apply layout/branding/search/tokenizer settings → Central platform engine"); that runtime surface is explicitly out of scope for this layer. Phase 15 may represent the configuration that such a runtime would one day consume, but it does not implement the resolution flow. This mirrors the ADR-0013 Decision posture ("No runtime resolution") carried into the configuration layer.

2. Caller-supplied identifiers only; replay safety.
   Every identifier-bearing field on a future Phase 15 artifact must accept a caller-supplied primitive only — no Date.now(), Math.random(), UUID generation, hash-derived identifiers, or crypto randomness at any step, and no default value, generated fallback, or internal derivation routine for identifier values.
   Grounding: REPLAY-SAFE GOVERNANCE LAW (HANDOFF_TEMPLATE.md §3), applied to structural artifact fields exactly as it was for the Phase 13/14 projectionId/deliveryId patterns (confirmed from the source contracts read in query-learning-interop/).

3. Immutability.
   Every externally exposed Phase 15 artifact must be deep-frozen via deepFreezeStructure(...). readonly alone and shallow Object.freeze are insufficient.
   Grounding: IMMUTABILITY LAW (HANDOFF_TEMPLATE.md §3).

4. Determinism.
   Equivalent inputs must produce equivalent configuration contracts and equivalent serialized output. No locale-aware collation; clone before sort; binary lexicographic ordering only.
   Grounding: DETERMINISTIC ORDERING LAW (HANDOFF_TEMPLATE.md §3); ARCHITECTURE.md — Deterministic Query Explainability ("Equivalent inputs must produce equivalent … serialized output").

5. Single-layer derivation; relationship to the Phase 14 delivery contracts deferred.
   Where a Phase 15 configuration artifact references delivery output, it must consume the Phase 14 route delivery contracts as the immediately preceding layer and must not reach through them to the Phase 13 projections or earlier.
   Grounding: SINGLE-LAYER GOVERNANCE DERIVATION LAW (HANDOFF_TEMPLATE.md §3); ARCHITECTURE.md — Delivery Boundary Layer / Layer Position ("Tenant and content configuration (Phase 15) consumes delivery contracts without reaching through Phase 13 internals").
   The available evidence settles the no-reach-through constraint but does not settle whether the core tenant/content configuration artifact (a) derives from a delivery contract, (b) composes with delivery contracts, or (c) is a parallel caller-supplied structural configuration layer with no preceding layer. ARCHITECTURE.md establishes that tenant/content configuration consumes delivery contracts, while tenant identity, enabled-language configuration, and content-organization settings are caller-supplied configuration with no obvious preceding-layer source. This ADR does not assert one of (a)/(b)/(c); the determination is deferred to the first Phase 15 slice's pre-implementation assessment under the DOCUMENTARY DERIVATION LAW and SINGLE-LAYER GOVERNANCE DERIVATION LAW (HANDOFF_TEMPLATE.md §3, §9).

6. Documentary grounding precondition; the Database Blueprint is not binding grounding.
   A Phase 15 structural contract field may be introduced only when it is grounded in BINDING repository evidence — ARCHITECTURE.md, DATA_SOURCES.md, or an existing type signature — per the DOCUMENTARY DERIVATION LAW (HANDOFF_TEMPLATE.md §3). The ARCHITECTURE.md — Database Blueprint candidate entities (tenants: "tenant identity, hostname/domain mapping, locale defaults, enabled languages, branding references, and feature flags"; dictionary_tenant_tags: "tenant-specific tagging, visibility, curation, lesson grouping, or search weighting") are CONCEPTUAL/ILLUSTRATIVE, not BINDING: ARCHITECTURE.md states "This schema is conceptual and subject to ADRs and future migration decisions. It does not select a production database, migration framework, hosting provider, or ORM," and the Explicit Non-Goals state "No production schema migrations yet." Decision: the Database Blueprint candidate entity fields are not sufficient grounding for any Phase 15 structural contract field. A binding ARCHITECTURE.md amendment that promotes specific tenant/content-configuration concepts from conceptual schema to architectural grounding is a precondition for the first Phase 15 code slice. This ADR establishes the boundary; it does not manufacture field grounding that the architecture documents withhold.

7. Language identity and the Typed Reference Law.
   Three language-related types exist in the repository, read from their definition files and confirmed mutually inconsistent:

   Resolution (post-acceptance): the canonical-language-identity precursor is resolved by ARCHITECTURE.md — Canonical Language Identity (BCP-47 codes; delivered set th/en; forward-only, no legacy migration). This ADR's §7 statement that none of the three existing types is a clean backing type stands; the resolution is a new canonical identity, not a reuse.

LexicalLanguageCode = "thai" | "en" (src/core/lexical/identity/lexical-entry-id.ts), embedded in LexicalEntryId = \${LexicalLanguageCode}:${string}:v${number}`` (same file);
LexicalLanguageDirection = "th→en" | "en→th" (src/core/lexical/contracts.ts) — a directional lookup pair, not a single-language identity;
SupportedLanguageCode = "th" | "zh" | "en" (src/core/tokenizers/drivers/tokenizer-driver.ts) — which uses "th" (vs LexicalLanguageCode's "thai") and includes "zh", a language module not delivered in the Thai-first repository. Decision: none of these is, as it stands, an unambiguous backing structural type for a tenant "enabled/configured language" concept — they disagree on the representation of Thai ("thai" vs "th") and on membership ("zh"). The TYPED REFERENCE LAW (HANDOFF_TEMPLATE.md §3) requires that, before any enabled-language configuration field is shaped as a string, the per-slice assessment confirm whether a backing structural type exists; the present evidence shows competing candidates and no canonical one. Whether a canonical language-identity type must be established first is therefore a precursor decision, deferred to per-slice pre-implementation assessment (and potentially to an ARCHITECTURE.md amendment per Decision §6). This ADR does not select among the three, does not propose a new type, and does not prescribe a field. The Phase 15/Phase 17 boundary is held: configuring which already-supported languages a tenant enables is Phase 15; adding or expanding a language module (e.g. Mandarin/"zh") is Phase 17 (ROADMAP.md — Phase 17 summary; SESSION_STATE.md — Deferred Scope). 8. Public-core / private-envelope boundary.
Phase 15 artifacts live in the public core and must carry only public/open configuration structure. Tenant-specific private data, premium educational content, proprietary AI prompts, monetization/analytics secrets, and private configuration keys must not appear in any Phase 15 public-core artifact.
Grounding: ARCHITECTURE.md — Public Core And Future Private Envelope (public core owns "shared platform infrastructure, governance files, open documentation"; the future private envelope owns "premium educational content, proprietary AI orchestration, monetization logic, analytics integrations, secrets, private prompts, and tenant-specific commercial data"); ARCHITECTURE.md — Core Architectural Principles ("Separate public/open data from premium, proprietary, or private data"); ARCHITECTURE.md — Explicit Non-Goals ("No proprietary content, private prompts, commercial datasets, analytics secrets, or tenant-specific private data in the public core"); DATA_SOURCES.md — Repository License Boundary and Dataset Governance Principles ("Keep public/open data separate from premium, proprietary, tenant-specific, or private data"); AGENTS.md — Data Boundaries and Safe Licensing.

9. File placement and shapes deferred.
   Exact type names, field names, builder signatures, schema version literals, slice count, and file placement are derived at per-slice pre-implementation assessment, following existing sibling topology exactly (one self-contained file colocating type, input, builder, and schema-version literal, under a domain subdirectory with a barrel — the confirmed pattern across lexical/reading/, lexical/spelling/, lexical/writing/, lexical/provenance/, and query-learning-interop/). This ADR describes the layer; it does not prescribe placement (HANDOFF_TEMPLATE.md §2, §12).

Schema version convention (for future slices, not introduced here). When a Phase 15 slice is later authorized and introduces a schema version literal, it must follow the established convention lingua-core-platform:<kebab-case-artifact-slug>@phase15 (HANDOFF_TEMPLATE.md §6 — Convention; SESSION_STATE.md — Schema Version Literals, where every phase-labelled literal observes this pattern). Per the Phase label invariant, no migration of any existing @phase9–@phase14 literal is warranted, and ARCHITECTURE.md defines no phase-coupled migration semantics (SESSION_STATE.md — Deferred Scope; Phase label invariant). This ADR introduces no schema version literal.

Structural Vocabulary
The following concepts are established as grounding vocabulary for Phase 15 pre-implementation assessments. Each cites its grounding by document and section or named law. No definition prescribes field names, interface members, builder parameters, or payload shapes; those are derived at assessment time under the DOCUMENTARY DERIVATION LAW and TYPED REFERENCE LAW (HANDOFF_TEMPLATE.md §3).

Tenant configuration (structural). The deterministic, caller-supplied, deep-frozen structural representation of a tenant's configuration. It is data describing a tenant, never the runtime act of resolving or applying a tenant. Grounded as a Phase 15 concept in ARCHITECTURE.md — Core Architectural Principles ("Keep tenant domains and language domains in one repository with clear internal module boundaries"), ARCHITECTURE.md — Delivery Boundary Layer / Layer Position (Phase 15 = "Tenant and content configuration"), and the conceptual ARCHITECTURE.md — Multi-Tenant Routing Concept / Database Blueprint tenants entity (CONCEPTUAL/ILLUSTRATIVE per Decision §6). The runtime resolution surface is excluded (STATIC RESOLUTION LAW). The specific structural members of tenant configuration are not grounded by any binding passage today and are subject to Decision §6.

Content configuration (structural). The deterministic structural representation of how a tenant organizes learning-surface content — lesson grouping, content sequencing, tenant-specific weighting, and curriculum organization — as static configuration data, not runtime sequencing, ranking, or adaptive selection. Grounded in ARCHITECTURE.md — Learning Surface Layer / Scope Boundaries ("Lesson grouping, sequencing, tenant-specific weighting, and curriculum organization belong to Phase 15 (tenant and content configuration)") and ADR-0011 Decision §3 ("Phase 15 owns grouping, sequencing, tenant-specific weighting, and lesson organization"). Any runtime ordering, ranking, weighting evaluation, or adaptive selection is excluded (STATIC RESOLUTION LAW; ARCHITECTURE.md — Deterministic Query Explainability, which bars introducing ranking).

Enabled-language configuration (structural). The structural representation of which already-supported platform languages a tenant enables. Grounded as a Phase 15 concern in ARCHITECTURE.md — Core Architectural Principles (tenant and language domains) and ARCHITECTURE.md — Multi-Tenant Routing Concept (conceptual "enabled languages"). Its typed representation is unresolved per Decision §7 (no canonical backing language type exists); the concept is named here, but no backing type is selected and no field is shaped. The Phase 15/17 boundary applies: enabling existing languages is Phase 15; adding language modules is Phase 17.

Single-layer consumption of delivery contracts. The constraint that any Phase 15 artifact referencing delivery output consumes the Phase 14 route delivery contracts directly and does not reach through to Phase 13 projections or earlier. Grounded in ARCHITECTURE.md — Delivery Boundary Layer / Layer Position and the SINGLE-LAYER GOVERNANCE DERIVATION LAW (HANDOFF_TEMPLATE.md §3). Whether such a reference exists at all (derive/compose/parallel) is deferred per Decision §5.

Prohibited Vocabulary
The following terms must not appear in any Phase 15 type name, field name, builder name, schema version literal, test description, or inline comment except where this ADR explicitly admits a structural-configuration sense. Each is classified individually with its governing citation. Where a term has both a runtime and a structural reading, the prohibited runtime concept is distinguished from any permitted structural-configuration-data concept.

lesson — ADMITTED as Phase 15 structural vocabulary in the sense of lesson grouping as static configuration data (ARCHITECTURE.md — Learning Surface Scope Boundaries; ADR-0011 Decision §3, which assign lesson grouping to Phase 15). PROHIBITED in any runtime sense — runtime lesson delivery, sequencing execution, or session-bound lesson state (STATIC RESOLUTION LAW; REPLAY-SAFE GOVERNANCE LAW). Supersedes the blanket ADR-0012 prohibition of "lesson," which was scoped to Phase 13.
exercise — INSUFFICIENTLY GROUNDED as a distinct Phase 15 structural concept. The structural exercise unit already belongs to Phase 12 (WritingPrimitive and its exerciseMode, confirmed from source); "exercise plan" was prohibited at Phase 13 (ADR-0012 Prohibited Vocabulary). No binding passage grounds a new Phase 15 "exercise" configuration concept. Any reintroduction requires binding ARCHITECTURE.md grounding (Decision §6). Runtime exercise evaluation/scoring remains PROHIBITED (ADR-0011 Decision §4; STATIC RESOLUTION LAW).
curriculum — ADMITTED as Phase 15 structural vocabulary in the sense of curriculum organization as static configuration data (ARCHITECTURE.md — Learning Surface Scope Boundaries: "curriculum organization belong to Phase 15"; ADR-0011 Decision §3). PROHIBITED in any adaptive/runtime sense — adaptive curriculum sequencing or learner-state-driven curriculum selection (STATIC RESOLUTION LAW; ADR-0012 precedent).
difficulty — STILL PROHIBITED as adaptive runtime vocabulary (ADR-0012 Prohibited Vocabulary; ADR-0013 grounding — "adaptive learning-state vocabulary; derived from no-runtime-resolution constraint"; STATIC RESOLUTION LAW). As a static content-classification datum it is INSUFFICIENTLY GROUNDED: it appears in DATA_SOURCES.md only as a candidate-dataset attribute ("difficulty classification for ReadingPrimitive content fields") contingent on a dataset reaching approved status, not as binding architectural grounding. No Phase 15 field may be grounded on it until that contingency is resolved (DOCUMENTARY DERIVATION LAW).
sequencing — ADMITTED as Phase 15 structural vocabulary in the sense of deterministic content sequencing expressed as static configuration data (ARCHITECTURE.md — Learning Surface Scope Boundaries: "sequencing … belong to Phase 15"). PROHIBITED in any runtime/adaptive sense — runtime sequence resolution or learner-adaptive ordering (STATIC RESOLUTION LAW; DETERMINISTIC ORDERING LAW; ADR-0012 precedent).
weighting — ADMITTED as Phase 15 structural vocabulary in the sense of tenant-specific weighting as a static configuration value (ARCHITECTURE.md — Learning Surface Scope Boundaries: "tenant-specific weighting … belong to Phase 15"). PROHIBITED in any runtime ranking/scoring sense — runtime search weighting evaluation or ranking (ARCHITECTURE.md — Deterministic Query Explainability, which bars introducing ranking; STATIC RESOLUTION LAW; ADR-0012 precedent on scoring).
visibility — STRUCTURAL reading INSUFFICIENTLY GROUNDED: "visibility" appears only in the CONCEPTUAL/ILLUSTRATIVE Database Blueprint dictionary_tenant_tags entity and in the non-grounding ROADMAP.md Phase 15 summary ("content visibility controls"); neither is binding (Decision §6; DOCUMENTARY DERIVATION LAW excludes ROADMAP summaries). RUNTIME content-visibility resolution is PROHIBITED (STATIC RESOLUTION LAW). A structural visibility-configuration concept requires a binding ARCHITECTURE.md amendment before use.
feature flag — RUNTIME feature-flag evaluation is PROHIBITED (STATIC RESOLUTION LAW — no runtime resolution / mutable singleton state; Decision §1). A STRUCTURAL "feature boundary as static configuration data" concept is INSUFFICIENTLY GROUNDED: "feature flags" appears only in the CONCEPTUAL Database Blueprint tenants entity and the non-grounding ROADMAP summary ("feature boundaries"). Binding grounding (Decision §6) is required before any such field.
branding — STRUCTURAL "branding references as configuration data" is INSUFFICIENTLY GROUNDED: it appears only in the CONCEPTUAL Database Blueprint tenants entity and the runtime ARCHITECTURE.md — Multi-Tenant Routing Concept ("Apply layout and branding settings") and the non-grounding ROADMAP summary. RUNTIME branding application is OUT OF SCOPE (runtime resolution; Decision §1; STATIC RESOLUTION LAW). Binding grounding required (Decision §6).
tenant — ADMITTED as Phase 15 structural vocabulary in the sense of the structural representation of tenant configuration (ARCHITECTURE.md — Core Architectural Principles; Delivery Boundary Layer / Layer Position naming Phase 15 "Tenant and content configuration"). PROHIBITED in any runtime sense — runtime tenant resolution, tenant routing, hostname/domain-to-tenant resolution, middleware tenant lookup, or request-context tenant application (STATIC RESOLUTION LAW; ADR-0013 Prohibited Vocabulary, which barred "tenant" at Phase 14 precisely because tenant resolution belongs to Phase 15's configuration concern, not to runtime).
Additionally carried forward as PROHIBITED at this layer (runtime-resolution and runtime-state indicators, grounded on named law and prior ADR precedent): router, middleware, hostname/domain resolution, runtime-resolve / middleware-resolved (STATIC RESOLUTION LAW; ADR-0013 Prohibited Vocabulary); session, cache, persistence/store (STATIC RESOLUTION LAW; REPLAY-SAFE GOVERNANCE LAW; ARCHITECTURE.md — Explicit Non-Goals on database/ORM); personalization, adaptive, recommendation, progress, mastery, scoring (ADR-0012/ADR-0013 precedent; STATIC RESOLUTION LAW); telemetry/analytics (ARCHITECTURE.md — Explicit Non-Goals; HANDOFF_TEMPLATE.md §11); authentication/auth (STATIC RESOLUTION LAW; ADR-0013 Prohibited Vocabulary).

Consequences
What this ADR makes possible. Phase 15 has a defined architectural boundary: a deterministic, caller-supplied, deep-frozen structural representation of tenant and content configuration, sitting after the Phase 14 delivery boundary in the layer stack, consuming delivery contracts single-layer where applicable and never reaching through to Phase 13 internals (ARCHITECTURE.md — Delivery Boundary Layer / Layer Position; SINGLE-LAYER GOVERNANCE DERIVATION LAW). It admits a grounded structural vocabulary for tenant configuration, content-organization configuration (lesson grouping, sequencing, tenant-specific weighting, curriculum organization), and enabled-language configuration, while drawing a firm line against the runtime tenant-resolution flow.

What remains prohibited at this layer. Runtime tenant resolution, routing, middleware, hostname/domain resolution, request-context application, feature-flag runtime evaluation, content-visibility runtime resolution, mutable/singleton/session state, async orchestration; persistence, database migrations, ORM, hosting and deployment topology; authentication and sessions; personalization, analytics/telemetry; adaptive/ranking/scoring behavior of any kind. Tenant-specific private data, premium content, proprietary prompts, analytics secrets, and private configuration keys must never appear in a public-core Phase 15 artifact. Discovery of any of these as a requirement during a Phase 15 pre-implementation assessment is a PA.8 conflict to be surfaced, not reconciled (HANDOFF_TEMPLATE.md §9 — PA.8; NO SPECULATIVE REMEDIATION LAW).

What must still be assessed before the first Phase 15 code slice.

A binding ARCHITECTURE.md grounding amendment that promotes specific tenant/content-configuration concepts from the CONCEPTUAL Database Blueprint to binding architectural grounding — a precondition under Decision §6, since no current binding passage grounds a Phase 15 contract field. Concluding that this amendment is required before any slice is the expected outcome of Decision §6, not a deferral of convenience.
The language-identity precursor decision (Decision §7): whether any existing language type is the backing type for enabled-language configuration, or whether a canonical language-identity type must be established first, while holding the Phase 15/Phase 17 boundary.
The single-layer relationship determination (Decision §5): whether the core tenant/content configuration artifact derives from, composes with, or is parallel to the Phase 14 delivery contracts.
Per-slice type names, field names, builder signatures, guard forms, schema version literal, slice count, and file placement, each grounded under the DOCUMENTARY DERIVATION LAW, TYPED REFERENCE LAW, ARTIFACT CLASSIFICATION LAW, INVARIANT GUARD FORM LAW, and existing sibling topology (HANDOFF_TEMPLATE.md §3, §9), and each requiring explicit operator authorization.
This ADR authorizes none of the above; it scopes them.
